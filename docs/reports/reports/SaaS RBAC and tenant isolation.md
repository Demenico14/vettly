# Build tenant walls in three layers

To make sure one organisation can never see or change another's data in a Next.js + Node.js + PostgreSQL SaaS, put three independent walls in place, each able to fail without causing a breach. **The first wall is a single server-side authorisation choke point.** Every Server Action, Route Handler and RPC method calls it. It denies by default, checks permissions rather than role names, and resolves the tenant from the authenticated membership rather than from the request. **The second wall is PostgreSQL Row-Level Security (RLS) on every tenant-scoped table.** The app connects as a non-owner, non-BYPASSRLS role, and the tenant ID is set with `set_config('app.tenant_id', $1, true)` inside each transaction, so a forgotten `WHERE organisation_id = ?` returns nothing instead of another tenant's rows. **The third wall is tenant-keyed discipline everywhere data leaves Postgres**: caches, object storage, job queues, search indexes, logs and CDN edges. The best-documented real cross-user leaks happened there, not in SQL. These walls matter because broken access control is the top web risk: OWASP found some form of it in **100% of applications tested** ([OWASP Top 10:2025 A01](https://top10.owasp.org/2025/A01_2025-Broken_Access_Control)). The closest real case to a recruitment product, McHire/Paradox.ai in 2025, combined a default `123456` admin password with an unchecked `lead_id` IDOR ([Ian Carroll](https://ian.sh/mcdonalds)). The law also counts. Under Zimbabwe's Cyber and Data Protection Act and SI 155 of 2024, and under South Africa's POPIA, a cross-tenant read is plausibly a notifiable breach. Zimbabwe gives the controller **24 hours** to tell the regulator, and POPIA requires the operator to tell the controller **"immediately"**. A SaaS processor serving both markets therefore needs logs that can scope an incident by tenant within hours, and contracts that promise notice well inside a day.

## Permissions, not roles, should be the unit your code checks

NIST's RBAC model (ANSI/INCITS 359-2004) defines a role as "essentially a collection of permissions". Permissions attach to roles, never directly to users. Core RBAC is mandatory, while role hierarchies and static or dynamic separation of duty are independent optional add-ons ([NIST CSRC RBAC FAQ](https://csrc.nist.gov/projects/role-based-access-control/faqs)). OWASP goes further for application code. It says ABAC and ReBAC "should typically be preferred", because role-presence checks are too coarse for object-level decisions, are easy to miss or chain incorrectly, and handle multi-tenancy poorly ([OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html)). The resolution is not to drop RBAC. Instead, use three layers. **Roles exist for administration**, for example org_admin, hr_manager, recruiter, hiring_manager and interviewer. **Permissions are what the enforcement point evaluates**, for example `candidate.read`, `candidate.read_sensitive`, `offer.approve`, `member.invite` and `role.assign`. **Relationship or attribute checks settle object-level questions**, such as whether this hiring manager is assigned to this requisition. Code should therefore call `can(ctx, 'candidate.read', candidate)` and never `if (role === 'recruiter')`. That way, renaming a role or adding per-tenant custom roles needs no code change. Per-tenant custom roles are now a mainstream B2B expectation: WorkOS supports organisation-scoped custom roles and maps identity-provider groups to roles ([WorkOS RBAC](https://workos.com/docs/rbac)).

ASVS 5.0 turns this into a deliverable. V8.1.1 (L1) requires written authorisation documentation that defines function-level and data-specific rules. V8.1.2 (L2) extends it to field-level read and write rules. V8.2.1–8.2.3 require explicit permission at the function, data-item and field level. V8.3.1 requires enforcement at a trusted service layer. **V8.4.1 (L2) requires cross-tenant controls so that a consumer's operations never affect tenants they have no permission to interact with** ([OWASP ASVS 5.0.0 V8](https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0/5.0/en/0x17-V8-Authorization.md)). A role × permission × resource-condition matrix is therefore an L1 artefact, not optional paperwork. The field-level layer matters for recruitment data, because a hiring manager may legitimately see a candidate record but not salary expectations, diversity data or right-to-work documents. The starting matrix below is a design proposal drawn from these principles. It is not taken from any one source.

| Role | Core permissions | Explicitly excluded |
|---|---|---|
| org_admin (keep two or more) | Members, roles, billing, SSO, retention settings, plus all HR permissions | `platform.*` (never assignable via tenant APIs) |
| hr_manager | All requisitions, candidates and offers; approve offers; configure pipelines; export reports | Billing, SSO, member roles |
| recruiter | Requisitions they own or are assigned to; candidates on those; schedule interviews; message candidates | Offer approval, member management |
| hiring_manager | Read candidates on assigned requisitions; scorecards; request offers | Exports, other requisitions, sensitive fields |
| interviewer | Own interview slots and scorecards | Everything else |

### One choke point, because Next.js has many doors

Every relevant standard says the same thing. Deny by default, implement authorisation once and reuse it, run it on every request for the specific object, and never rely on client-side checks or hidden IDs ([OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html); [OWASP Top 10:2025 A01](https://top10.owasp.org/2025/A01_2025-Broken_Access_Control)). OWASP API5 asks for one consistent authorisation module that every business function calls, with "explicit grants to specific roles for access to every function". Its example attack is directly relevant to invitations: an attacker swaps `GET /api/invites/{guid}` for an unprotected `POST /api/invites/new` and mints an admin invite ([OWASP API5:2023](https://api-security.owasp.org/editions/2023/en/0xa5-broken-function-level-authorization)). API1 adds that comparing the session user ID with a requested ID "isn't a sufficient solution" ([OWASP API1:2023](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization)). The IDOR cheat sheet's preferred fix is to scope the lookup itself to the caller's data, as in `current_user.projects.find(id)` rather than `Project.find(id)`. It also says to return the same 404 for "not found" and "not yours" ([OWASP IDOR Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Insecure_Direct_Object_Reference_Prevention_Cheat_Sheet.html)).

Next.js makes the choke point essential because it has many entry points. The official guidance is a server-only Data Access Layer (DAL) that centralises data requests and authorisation and returns DTOs with only the needed fields. Proxy (formerly middleware) is for optimistic redirects only and "should not be your only line of defense". Layouts do not re-render on navigation, so checks placed there do not run for every route ([Next.js Authentication guide](https://nextjs.org/docs/app/guides/authentication)). Server Actions are reachable by direct POST even if no page imports them, and a page-level auth check does not cover actions defined on that page ([Next.js Data Security guide](https://nextjs.org/docs/app/guides/data-security)). **CVE-2025-29927 (CVSS 9.1) showed the cost of trusting middleware.** A crafted `x-middleware-subrequest` header skipped middleware entirely on self-hosted `next start` and standalone deployments. The fix shipped in 14.2.25 and 15.2.3, with backports to 13.5.9 and 12.3.5 ([Vercel postmortem](https://vercel.com/blog/postmortem-on-next-js-middleware-bypass); [NVD](https://nvd.nist.gov/vuln/detail/CVE-2025-29927)).

The concrete shape is a server-only `authz` module (marked `import 'server-only'`) that takes `{ principal, orgId, action, resource }` and sits in front of a repository layer. Repository methods accept only a tenant-bound context and always add `WHERE organisation_id = ctx.orgId`. Raw ORM access from handlers is lint-banned. The `orgId` comes from the authenticated membership, or from a URL slug validated against the user's memberships, and never from a request body. Writes are object-level authorisation too: "attach candidate X to job Y" must verify that *both* IDs belong to the caller's org.

### Dynamic RPC dispatch is a hidden function-level hole

A dispatcher such as `services[service][method](args)` on `/api/rpc/<service>/<method>` can reach inherited `Object.prototype` members (`constructor`, `toString`, `__defineSetter__`) or unscoped internal helpers. CodeQL flags this pattern as `js/unvalidated-dynamic-method-call`. It recommends a `Map` of handlers checked with `has()` and `typeof === 'function'`, or an explicit allowlist ([CodeQL](https://codeql.github.com/codeql-query-help/javascript/js-unvalidated-dynamic-method-call/)). Prototype pollution makes this worse, because `Object.prototype` is shared across the whole Node process. One polluting request can make `user.isAdmin` truthy for every later request ([MDN](https://developer.mozilla.org/en-US/docs/Web/Security/Attacks/Prototype_pollution)). OWASP's prevention advice is to use `Map`/`Set` and `Object.create(null)` for keyed data. It treats `--disable-proto` as defence in depth only, because `constructor.prototype` pollution still works ([OWASP Prototype Pollution Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Prototype_Pollution_Prevention_Cheat_Sheet.html)). The fix is a frozen registry, `new Map([['candidates.get', { handler, permission: 'candidate.read' }], ...])`. The dispatcher returns 404 for unknown names and **fails closed when a method has no declared permission**. Request bodies are validated with strict schemas that reject `__proto__` and `constructor` keys, and permission and role maps are checked with `Object.hasOwn` rather than truthiness.

## Escalation stops at four rules: subset, no-self, last-admin, step-up

The clearest published rule against privilege escalation comes from Kubernetes RBAC. A principal may create or edit a role only if it already holds every permission in it, and may bind a role only if it holds all of that role's permissions. The only exception is an explicit `escalate` or `bind` privilege ([Kubernetes RBAC](https://kubernetes.io/docs/reference/access-authn-authz/rbac/)). Applied to SaaS, the rule is that `assignRole(actor, target, role)` requires `role.assign` **and** `permissions(role) ⊆ permissions(actor)`. The same subset check applies when someone edits a custom role definition. This one rule closes the classic attack where an HR manager grants themselves or an ally org_admin. Three product conventions complete the set. GitHub owners cannot change their own role, and GitHub recommends at least two owners per organisation ([GitHub Docs](https://docs.github.com/en/organizations/managing-peoples-access-to-your-organization-with-roles/maintaining-ownership-continuity-for-your-organization)). Slack's primary owner cannot be deactivated until ownership is transferred ([Slack](https://slack.com/help/articles/204475027-Deactivate-a-members-account)). GitHub's sudo mode re-prompts for authentication before invitations, adding members and changing team roles, and the elevated window lasts two hours ([GitHub sudo mode](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/sudo-mode)). In practice, the role API should do four things. It rejects `actor.id === target.id`. It refuses, in the same transaction, any demotion, removal or departure that would leave zero active org_admins, using `SELECT ... FOR UPDATE` on the org's admin memberships to stop two concurrent demotions racing. It validates the role value against a server-side allowlist. And it requires a recent authentication before elevated invites, role changes, member removal, SSO changes and exports.

### Invitations are credentials, and they have their own CVEs

An invitation grants access, so it deserves the same care as a password-reset token. CVE-2025-66223 documented every common mistake at once: tokens that never expired, tokens that stayed valid after the invitee was removed, and several invites with different roles for one email ([Rapid7](https://www.rapid7.com/db/vulnerabilities/cve-2025-66223/)). Auth0's Organizations model shows the correct binding. The invitee must sign in with the email the invite was sent to, and roles apply only within that organisation ([Auth0](https://auth0.com/docs/manage-users/organizations/configure-organizations/invite-members)). A sound acceptance flow works like this. It hashes the presented token and looks it up. It checks the token is not expired, accepted or revoked. It requires that the user's verified email equals the invited email. It re-checks that the inviter still holds `member.invite` and the subset rule at acceptance time, not only at creation. It creates the membership for the invitation's stored `org_id`, never one taken from the request. Finally, it marks the invitation consumed in the same transaction. The 7-day expiry commonly used comes from vendor and practitioner practice; no standard prescribes it.

### Role changes must bite on the next request, not next week

ASVS 8.3.2 (L3) requires that changes to authorisation-relevant values take effect immediately ([ASVS 5.0.0 V8](https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0/5.0/en/0x17-V8-Authorization.md)). OWASP requires the session ID to be regenerated "after any privilege level change" ([OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)). The Next.js example JWT session lasts 7 days, while the docs describe database sessions as "more secure" and able to support "log out of all devices" ([Next.js Authentication guide](https://nextjs.org/docs/app/guides/authentication)). So the session should carry identity only. **Membership, role and status should be read from Postgres on every Server Action, Route Handler and API request**, optionally cached for seconds and invalidated explicitly when they change. On removal, mark the membership removed, revoke that user's sessions and API keys for the org, and cancel any pending invites they issued. On elevation, rotate the session token.

### Platform staff belong in a separate realm

Support and platform engineers should not be tenant members holding org_admin. WorkOS's impersonation design is a good template. The operator must give a reason, which is recorded on the session-created event. Sessions expire after **60 minutes**. The session carries an `impersonator` field, and only environment admins can enable the feature ([WorkOS impersonation](https://workos.com/docs/authkit/impersonation)). ASVS 8.3.3 (L3) requires decisions based on the originating consumer's permissions, and 8.4.2 (L3) requires admin interfaces to use more than network location ([ASVS 5.0.0 V8](https://raw.githubusercontent.com/OWASP/ASVS/v5.0.0/5.0/en/0x17-V8-Authorization.md)). The OWASP Logging Cheat Sheet requires logging all administrator actions and all break-glass use ([OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)). In practice this means a `platform.*` permission namespace that tenant APIs can never grant. Cross-tenant access goes only through a time-boxed support-session record (staff ID, tenant, reason, ticket, expiry). Every action is stamped with both `actor=staff` and `on_behalf_of=user`. Role changes, exports and deletes are blocked during impersonation. Whether to require customer consent for support access is a design choice; the research notes found no primary source on it.

## Row-Level Security catches the filter you forgot — if you avoid five traps

AWS states the case plainly: in a pooled PostgreSQL model, "Row-level security (RLS) is required to maintain tenant data isolation" ([AWS Prescriptive Guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/saas-multitenant-managed-postgresql/pool.html)). Azure says a shared database gives "the highest density of tenants" at "the lowest financial cost". It also warns that RLS "can be complex to design, implement, test, and maintain", and that table-per-tenant is an antipattern ([Azure Architecture Center](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/storage-data)). Citus's experience with schema-per-tenant was that migrations stretched "from seconds to minutes to hours across thousands of different tenants" ([Citus](https://www.citusdata.com/blog/2016/12/18/schema-sharding-lessons/)). For a single shared database with `organisation_id` keys, the vendor consensus is to keep the pool model and harden it with RLS. Keep a dedicated-database "stamp" in reserve for enterprise tenants who need their own keys, residency or per-tenant restore, which Azure names as the three triggers for isolating a tenant. RLS is a backstop, not a replacement for application scoping. It does not isolate CPU or cache ([Nile](https://www.thenile.dev/blog/multi-tenant-rls)), and it fails silently: a blocked UPDATE simply affects 0 rows.

### Trap one: the app connects as a role that bypasses RLS

"Superusers and roles with the BYPASSRLS attribute always bypass the row security system." Table owners bypass it too, unless `FORCE ROW LEVEL SECURITY` is set ([PostgreSQL 16 docs](https://www.postgresql.org/docs/16/ddl-rowsecurity.html)). Nile's team found its tests were silently passing because the app connected as a privileged role ([Nile](https://www.thenile.dev/blog/multi-tenant-rls)). The fix is three roles. **`app_owner`** owns the schema and runs drizzle-kit migrations through a separate `MIGRATION_DATABASE_URL`. **`app_user`** has DML grants only and is `NOSUPERUSER NOBYPASSRLS`. An optional **`app_admin`** with BYPASSRLS is used only by audited platform code paths. Then `ENABLE` **and** `FORCE` RLS on every tenant table. `ALTER DEFAULT PRIVILEGES FOR ROLE app_owner` grants new tables to `app_user` automatically, because default privileges apply only to objects created by the named role ([PG16 ALTER DEFAULT PRIVILEGES](https://www.postgresql.org/docs/16/sql-alterdefaultprivileges.html)). Crunchy Data recommends one shared application role plus a session variable rather than a database role per tenant, because per-tenant roles defeat connection pooling ([Crunchy Data](https://www.crunchydata.com/blog/row-level-security-for-tenants-in-postgres)).

```sql
ALTER TABLE records ENABLE ROW LEVEL SECURITY;
ALTER TABLE records FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON records
  AS PERMISSIVE FOR ALL TO app_user
  USING      (organisation_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid)
  WITH CHECK (organisation_id = NULLIF(current_setting('app.tenant_id', true), '')::uuid);
```

### Trap two: a session-level SET leaks through the pool

`set_config(name, value, is_local)` with `is_local = true` lasts only for the current transaction ([PG16 admin functions](https://www.postgresql.org/docs/16/functions-admin.html)). Plain `SET` lasts for the whole session, and in a pool a "session" is a connection that the next, unrelated request will reuse. The postgres.js README is explicit: in both pooling modes a session belongs to a client "only for the length of a transaction". It also says `sql.begin` reserves one connection and hands you a scoped `sql` instance ([postgres.js](https://github.com/porsager/postgres)). PgBouncer in transaction mode does not run `server_reset_query`, so session state is never cleaned up between clients ([PgBouncer](https://www.pgbouncer.org/config.html)). Nile hit the application-side version of this bug: an RLS identity stored in thread-local storage carried into the next request on a reused thread ([Nile](https://www.thenile.dev/blog/multi-tenant-rls)). The safe pattern with Drizzle mirrors the transaction-scoped `set_config` in Drizzle's own Supabase example ([Drizzle RLS docs](https://orm.drizzle.team/docs/rls)):

```ts
export async function withTenant<T>(orgId: string, fn: (tx: Tx) => Promise<T>) {
  if (!isUuid(orgId)) throw new Error('missing tenant');               // fail closed in app
  return db.transaction(async (tx) => {
    await tx.execute(sql`select set_config('app.tenant_id', ${orgId}, true)`); // bound param, txn-local
    return fn(tx);
  });
}
```

Every query in the request must use `tx`. A stray global `db.select()` runs on another pooled connection with no tenant set and returns nothing. That fails closed, but it surfaces as a confusing bug, so enforce `tx`-only access through the repository layer. When using PgBouncer in transaction mode, set `prepare: false` unless you run PgBouncer 1.21 or later with `max_prepared_statements` configured ([postgres.js](https://github.com/porsager/postgres)).

### Trap three: the empty-string ghost

`current_setting(name, true)` returns NULL when a setting has never existed ([PG16 admin functions](https://www.postgresql.org/docs/16/functions-admin.html)). But once a custom setting has been SET on a connection, even with SET LOCAL, it "springs into existence" with an empty-string default. Later transactions on that connection then read `''`, not NULL ([pgsql-bugs thread](https://www.postgresql.org/message-id/CA+Q86ij0KDCB0G45G509-8q0DNR611gcKG-sSM83GA1EBL7boA@mail.gmail.com)). Wrapping the value in **`NULLIF(..., '')`** makes the predicate NULL, so no rows are visible and inserts fail WITH CHECK. A garbage value fails the `::uuid` cast, which also fails closed. Crunchy uses this same defensive form ([Crunchy Data](https://crunchydata.com/blog/row-level-security-for-tenants-in-postgres)).

### Trap four: policy semantics that widen or hide

With RLS enabled and no policy, access is default-deny. USING silently filters rows, while WITH CHECK raises an error on bad new rows. Permissive policies combine with OR, so adding one broad "admin" policy widens access for everyone. Use `AS RESTRICTIVE` or a single combined policy instead ([PG16 docs](https://www.postgresql.org/docs/16/ddl-rowsecurity.html); [Bytebase](https://www.bytebase.com/blog/postgres-row-level-security-footguns/)). The best-performing policy considers only the current row. Sub-SELECTs inside policies can leak under READ COMMITTED races ([PG16 docs](https://www.postgresql.org/docs/16/ddl-rowsecurity.html)). So check membership once in the app and keep the policy a plain equality. Index every policy column, leading with `organisation_id` ([Supabase RLS docs](https://supabase.com/docs/guides/database/postgres/row-level-security)). Drizzle adds its own trap. With plain `pgTable`, removing a table's last policy makes drizzle-kit *disable* RLS on that table. `pgTable.withRLS(...)` keeps RLS on regardless ([Drizzle RLS docs](https://orm.drizzle.team/docs/rls)). The research found no confirmation that drizzle-kit emits `FORCE`, so add it in a custom SQL migration.

### Trap five: paths that run as someone else or copy data out

By default, views apply the *view owner's* policies. On PG15 and later, `security_invoker = true` makes them apply the caller's policies instead ([PG16 CREATE VIEW](https://www.postgresql.org/docs/16/sql-createview.html)). A SECURITY DEFINER function owned by a BYPASSRLS role skips RLS entirely, so give such functions a pinned `search_path` and schema-qualified names ([Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security)). Unique, primary-key and foreign-key checks "always bypass row security", so a duplicate-key error can reveal that a value exists in another tenant ([PG16 docs](https://www.postgresql.org/docs/16/ddl-rowsecurity.html)). Scope unique indexes per tenant, for example `(organisation_id, lower(email))` ([Bytebase](https://www.bytebase.com/blog/postgres-row-level-security-footguns/)). Use composite foreign keys that include `organisation_id`, so a row in one tenant cannot reference a parent row in another. Materialised views, exports and background jobs copy data beyond the reach of policies ([Bytebase](https://www.bytebase.com/blog/postgres-row-level-security-footguns/)). Prefer UUIDs to shared serial IDs; this is an inference from the docs' surrogate-key advice, because a global counter reveals other tenants' activity volume. Tables read before the tenant is known, such as `users`, `sessions` and `tokens`, need a deliberate per-table design: a user-keyed policy, narrowly scoped definer functions, or exclusion from RLS protected by grants and app logic.

Testing must run as `app_user`, because tests run as superuser or owner "falsely pass" ([Bytebase](https://www.bytebase.com/blog/postgres-row-level-security-footguns/)). The suite should prove the following. A cross-tenant SELECT by primary key returns 0 rows. A cross-tenant UPDATE or DELETE affects 0 rows. An INSERT with another tenant's ID fails with SQLSTATE 42501. A query with no tenant set returns nothing. A tenant setting does not survive into the next transaction on the same reserved connection. Finally, a catalog assertion checks that every table with an `organisation_id` column has `relrowsecurity` and `relforcerowsecurity` set and at least one policy, and that the app role is neither superuser, BYPASSRLS nor a table owner. That last test is the one that catches next quarter's new table.

## Caches and edges, not SQL, produced the famous leaks

The best-documented cross-user exposures happened in infrastructure that sat in front of correct authorisation code. On **20 March 2023**, a redis-py asyncio bug left a pooled Redis connection holding a cancelled request's response. The next user on that connection received someone else's cached data. For about **1.2% of ChatGPT Plus subscribers** active in a nine-hour window, that included name, email, billing address and the last four card digits. OpenAI's fix included "checks to confirm cached data matches the requesting user" ([OpenAI](https://openai.com/index/march-20-chatgpt-outage/)). On Christmas Day 2015, a CDN caching rule deployed during a DoS attack served authenticated Steam store pages for about **34,000 users** to other people ([Steam](https://store.steampowered.com/news/19852)). More recently, Asana took its new MCP server offline from 5 to 17 June 2025 after a bug "could have potentially exposed certain information from your Asana domain to other Asana MCP users" ([The Register](https://www.theregister.com/2025/06/18/asana_mcp_server_bug/)). The pattern is consistent. **New code paths, shared infrastructure and permissive defaults are where isolation breaks.** ChaosDB showed how long-lived keys extend the damage: a default-on notebook feature let Wiz reach the primary keys of several thousand Cosmos DB customers, and Microsoft told more than 30% of customers to rotate ([Wiz](https://www.wiz.io/blog/chaosdb-how-we-hacked-thousands-of-azure-customers-databases)).

These incidents translate into a few controls for each store outside Postgres. For an **in-process per-org cache**, key every entry `${orgId}:${entity}:${id}` and assert `entry.orgId === ctx.orgId` on read, as OpenAI now does. Use `Map` containers. Never hold request-scoped state such as "current org" in module scope, because Node and serverless processes serve concurrent requests; use AsyncLocalStorage or pass `ctx` explicitly. For **edges**, authenticated responses must send `Cache-Control: private, no-store`, which OWASP also requires for responses carrying session data ([OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)).

For **S3-compatible storage**, remember that presigned URLs are bearer tokens. They can be reused until expiry, which can be up to 7 days with SigV4 and IAM user keys. Expiry is checked only when a request starts. And a presigned PUT overwrites any existing object at that key ([AWS S3 docs](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)). So issue URLs only after an org-scoped authorisation check on the document record, with expiries measured in minutes, backed by an `s3:signatureAge` bucket-policy deny. Use server-generated random keys under `org/<orgId>/`, and never treat the prefix alone as authorisation. Block public access, and never log signed URLs, because the URL is the credential.

For **CV-processing jobs**, carry `orgId` in every payload. The worker re-loads the record through `withTenant(orgId)` rather than trusting payload IDs, and writes parsed fields, extracted text and embeddings only under that org. Any search or vector index needs an `orgId` field on every document and a mandatory tenant filter on every query. **Exports** must reuse the org-scoped data layer rather than a bespoke "export all" query. **Error messages** must not confirm that IDs exist in other tenants.

**Uploads** follow ASVS V5. Enforce size limits (5.2.1). Check that content matches the extension by magic bytes (5.2.2). Never execute uploaded files (5.3.1). Ignore user-supplied filenames and set an RFC 6266-encoded `Content-Disposition` (5.4.1–5.4.2). Antivirus-scan untrusted files before serving them (5.4.3) ([ASVS 5.0 V5](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x14-V5-File-Handling.md)). Serve them as `attachment` with `nosniff`, ideally from a separate download hostname, so a malicious CV cannot render in the app's origin (ASVS 3.2.1, 3.5.4) ([ASVS 5.0 V3](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x12-V3-Web-Frontend-Security.md)).

## Session, login and header hardening maps cleanly onto ASVS and NIST

Session tokens should be opaque, generated by a CSPRNG and carry at least 128 bits (ASVS 7.2.3). Store only their hash; SHA-256 is adequate at that entropy, by the same logic ASVS 6.5.2 applies to secrets above 112 bits ([ASVS 5.0 V7](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x16-V7-Session-Management.md); [V6](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x15-V6-Authentication.md)). The cookie should be `__Host-vettly_session=…; Path=/; Secure; HttpOnly; SameSite=Lax`. The `__Host-` prefix stops a sibling subdomain from overwriting it. Lax keeps emailed deep links working. NIST 800-63B-4 §5.1.1 says cookie expiry "SHALL NOT be relied upon to enforce session timeouts", so idle and absolute limits live in database columns ([NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)). For AAL2, NIST says sessions SHOULD last no more than **24 hours absolute and 1 hour idle**. ASVS 7.1.1 lets a product deviate if it documents the justification, which allows a longer idle limit for an all-day hiring tool. Rotate the token on every authentication and privilege change (7.2.4). Kill all sessions on account disable (7.4.2). Offer to kill other sessions after a password or MFA change (7.4.3); a B2B default of revoking them is defensible. Let users view and terminate their own sessions (7.5.2).

CSRF needs layers because "SameSite is useful as a defense-in-depth control but it does not replace a proper CSRF defense" ([OWASP CSRF Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)). Next.js Server Actions are POST-only and already compare `Origin` with `Host`. Custom `route.ts` handlers and a separate Node API get no such check ([Next.js Data Security guide](https://nextjs.org/docs/app/guides/data-security)). So the API's middleware for unsafe methods should do three things. It rejects `Sec-Fetch-Site: cross-site`. It falls back to an exact `Origin` allowlist, rejecting a missing or `null` Origin. And it requires `Content-Type: application/json` or a custom header so that cross-origin calls must preflight (ASVS 3.5.1–3.5.3). CORS stays locked to the app origin.

Passwords follow NIST 800-63B-4 §3.1.1.2. They must be **at least 15 characters when used alone, or at least 8 when paired with MFA**. Accept at least 64 characters, impose no composition rules or forced rotation, and check new passwords against breach corpuses ([NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)). Hash with Argon2id at m=19 MiB, t=2, p=1 or stronger, or with scrypt at N=2^17, r=8, p=1, storing parameters in PHC format and rehashing on upgrade ([OWASP Password Storage Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)). Throttle per account with exponential backoff rather than hard lockouts, which attackers can abuse for denial of service. Stay well under NIST's ceiling of 100 consecutive failures. Return identical messages and timing for known and unknown accounts ([OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)).

For MFA, NIST requires AAL2 verifiers to offer at least one phishing-resistant option. Syncable passkeys qualify at AAL2, while TOTP is acceptable but not phishing-resistant. Require MFA for org_admins (ASVS 6.3.3) and prefer passkeys. Store `auth_time` and `amr` on the session row. Before role changes, admin invites, bulk candidate exports, SSO changes and org deletion, require a fresh authentication within a short window, then rotate the token (ASVS 7.5.1, 7.5.3). The window length is a design choice, because neither ASVS nor NIST sets a number.

The candidate flow (an emailed link plus a 6-digit code) is email-possession verification, not a NIST authenticator; §3.1.3.1 says email "SHALL NOT" be used for out-of-band authentication. It meets the ASVS 20-bit floor only if the code is single-use, expires within 10 minutes, is rate-limited and is bound to its invitation (ASVS 6.5.1, 6.5.4, 6.5.5, 6.6.2–6.6.3). Record this as a documented risk decision.

Security headers go in `next.config.js` `headers()`, with a per-request CSP nonce set in `proxy.ts`. Nonces force dynamic rendering and are incompatible with Partial Prerendering, so marketing pages can use static CSP or the experimental SRI option instead ([Next.js CSP guide](https://nextjs.org/docs/app/guides/content-security-policy)). Self-hosted multi-instance deployments must set `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`. Only server-only modules should read secrets, and `NEXT_PUBLIC_*` variables are shipped to the client ([Next.js Data Security guide](https://nextjs.org/docs/app/guides/data-security)).

Audit logging records who, what, when, where, the object, the result and the reason (ASVS 16.2.1). Never log credentials, and hash session tokens before logging them (16.2.5). Log every failed authorisation (16.3.2), and ship logs to a separate system (16.4.3) ([ASVS 5.0 V16](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x25-V16-Security-Logging-and-Error-Handling.md)). OWASP adds tamper detection, a separate restricted database account for writing logs, and alerts when logging stops ([OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)). In Postgres, that means an `audit_events` table where the app role has INSERT only. Each row is written in the same transaction as the change it records. Reads and exports of sensitive candidate fields are logged too, not only writes.

## Zimbabwe and South Africa turn a cross-tenant bug into a reportable offence

Neither statute mentions RBAC or multi-tenancy. Both, however, impose duties that only strong tenant isolation can meet.

### Zimbabwe: the CDPA and SI 155 of 2024

**Zimbabwe's CDPA** has applied since 11 March 2022, with POTRAZ as the Data Protection Authority. Section 18 requires "appropriate technical and organisational measures" against unauthorised access and alteration. Section 17 limits processors to acting "only as instructed by the controller". Section 18(5) requires a written controller–processor contract. Section 19 requires notice to the Authority **within 24 hours** of any security breach ([CDPA](https://www.veritaszim.net/sites/veritas_d/files/Cyber%20%26%20Data%20Protection%20Act%20Cap1207%20No%205%20of%202021%20gaz%202022-03-11.pdf)).

**SI 155 of 2024**, gazetted 13 September 2024, sharpens these duties considerably ([SI 155](https://www.veritaszim.net/sites/veritas_d/files/SI%202024-155%20Cyber%20and%20Data%20Protection%20(Licensing%20of%20Data%20Controllers%20and%20Appointment%20of%20Data%20Protection%20Officers)%20Regulations,%202024.pdf)):

- Section 16 requires controllers and processors to *test* their measures and improve them.
- Section 17 adds notice to data subjects within **72 hours** for high-risk breaches, a breach investigation report within **21 days**, "robust breach detection", and a breach register. The regulator's report form (DP3) asks for the systems affected and approximate record counts.
- Controllers need an annual licence in one of four tiers, priced from USD 50 for 50–1,000 data subjects to USD 2,500 for more than 500,000.
- Every controller must appoint a DPO who holds a certification approved by POTRAZ.
- Controllers must notify POTRAZ in advance of any intended transfer outside Zimbabwe (s10(2)(c)).

Breaches of these provisions are criminal offences, punishable by a **level 11 fine, up to 7 years' imprisonment, or both**.

Two features of Zimbabwean law matter especially for a recruitment product. First, the "sensitive data" definition includes "gender, age, marital status or family status" and educational, financial or employment history, and section 11 requires written consent to process it. Ordinary CV fields therefore appear to be sensitive data, which strengthens the case for field-level access control across the whole candidate record. Second, the SI 155 licensing trigger covers anyone processing "with the intention to obtain a commercial gain". That wording arguably reaches a SaaS processor, and the research found no guidance either way. Local press reports that POTRAZ began risk-based inspections on 1 September 2026 ([Post on Sunday](https://postonsunday.co.zw/2026/08/17/potraz-sets-september-deadline-for-data-protection-compliance/)). No published enforcement decisions were found.

### South Africa: POPIA

**POPIA** classifies a SaaS provider that processes data for employers as an "operator". Section 19 requires risk-based safeguards that are "regularly verified" and updated, with due regard to generally accepted security practice ([POPIA s19](https://popia.co.za/section-19-security-measures-on-integrity-and-confidentiality-of-personal-information/)). Section 21 requires a written contract that imposes those safeguards on the operator. It also obliges the operator to notify the responsible party **immediately** when there are reasonable grounds to believe unauthorised access has occurred ([POPIA s21](https://popia.co.za/section-21-security-measures-regarding-information-processed-by-operator/)). Section 22 then requires the responsible party to notify the Information Regulator and the data subjects "as soon as reasonably possible" ([POPIA s22](https://popia.co.za/section-22-notification-of-security-compromises/)). Since 1 April 2025 those notifications must go through the Regulator's eServices portal ([Inside Privacy](https://www.insideprivacy.com/data-security/data-breaches/south-africa-introduces-mandatory-e-portal-reporting-for-data-breaches/)).

Enforcement is real and directly about security safeguards:

- The Department of Justice received a **R5m** infringement notice after ransomware, citing expired security licences and an outdated incident response plan ([Norton Rose Fulbright](https://nortonrosefulbright.com/en/news/287987e5/information-regulator-issues-first-fine-to-the-department-of-justice-after-ransomware-attack)).
- Lancet Laboratories paid **R100,000** for failing to report security compromises ([IR media briefing, Nov 2025](https://inforegulator.org.za/wp-content/uploads/2025/11/MEDIA-STATEMENT_INFORMATION-REGULATORS-LATEST-UPDATE-Journalist-ver.pdf)).
- In 2026 the Regulator ordered SABS to fix its safeguards within 90 days. It stressed that it acted on the compliance failings, not because SABS had been attacked ([Werksmans](https://werksmans.com/the-regulator-is-watching-new-enforcement-signals-for-popia-and-paia-compliance/)).

The Regulator received **2,374 breach notices in 2024/25**, and the monthly rate rose about 40% in the following months ([IR media briefing](https://inforegulator.org.za/wp-content/uploads/2025/11/MEDIA-STATEMENT_INFORMATION-REGULATORS-LATEST-UPDATE-Journalist-ver.pdf)).

### Both regimes: transfers and automated decisions

Both regimes restrict transfers abroad. In Zimbabwe, sections 28–29 of the CDPA require adequacy or a listed derogation, and the Act provides no express standard-contractual-clause route. In South Africa, section 72(1)(a) of POPIA accepts a binding agreement or binding corporate rules. Both also restrict solely automated decisions: section 25 of the CDPA, which SI 155 makes a controller duty, and section 71 of POPIA, which expressly names "performance at work" as a profiling factor ([POPIA s71](https://popia.co.za/section-71-automated-decision-making/)).

### What this means for the product and contracts

The engineering consequences follow directly. A cross-tenant read caused by an authorisation bug is plausibly a notifiable breach under both regimes. That is an inference: no source settles whether an internal exposure with no sign of exfiltration crosses either threshold. The processor agreement therefore needs a **notice commitment well under 24 hours**, because a 72-hour promise would leave Zimbabwean customers unable to meet their own deadline. Per-tenant audit logs must be able to say, within hours, which tenant's records an actor reached and how many, because both the DP3 form and the POPIA notice ask for that.

Several product features serve both laws at once:

- Region-aware hosting metadata, which helps customers complete the location question on their licence form (DP1) and file transfer notices.
- Per-tenant retention settings and deletion with evidence of what was deleted.
- Per-candidate export to answer access requests.
- A role-gated human review step before any adverse AI-assisted outcome, logging the reviewer's identity and rationale.

These notes are research findings, not legal advice. In particular, the USD value of a level 11 fine and the licensing position of pure processors remain unverified.

## Conclusion

Tenant isolation has shifted from a query-writing discipline to a systems property. The SQL `WHERE` clause is the part teams rarely get wrong. The failures come from the places around it: a new entry point added beside the choke point (Asana's MCP server, the Next.js middleware bypass), a pooled connection carrying the previous request's state (Redis at OpenAI, `SET` behind PgBouncer, thread-locals at Nile), or a privileged role that silently turns RLS off. The design goal is therefore not "check the tenant everywhere". It is to make the unchecked path impossible or empty. A dispatcher that refuses methods with no declared permission, a repository that only accepts a tenant-bound transaction, and a database that returns zero rows when the tenant is missing each convert a future bug from a breach into a failed test.

The legal analysis adds a less obvious requirement: **forensic precision matters almost as much as prevention.** Zimbabwe's 24-hour clock and POPIA's "immediately" for operators mean that a SaaS vendor serving both markets will be judged on how fast it can say which tenant, which records and which actor, as well as on whether isolation held. The in-transaction, INSERT-only audit trail and the registry-driven cross-tenant test suite do double duty. They are the strongest engineering controls, and they are also the evidence that SI 155 s16 and POPIA s19 expect: proof that safeguards are tested and verified regularly, not merely written down.
