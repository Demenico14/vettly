# Session Management and Web-Application Security for a Cookie-Authenticated Next.js B2B SaaS

Context assumed: Next.js App Router frontend, Node.js JSON API, opaque random session tokens stored as SHA-256 hashes in Postgres, cookie `vettly_session`; candidates use emailed links plus a 6-digit email code and a per-invitation cookie. Standards checked: OWASP ASVS 5.0 (GitHub master, `5.0/en`), NIST SP 800-63B-4 (final, pages.nist.gov/800-63-4), OWASP Cheat Sheets, Next.js docs (CSP guide last updated 2026-03-20; Data Security guide last updated 2026-11-18). ASVS requirement text below is paraphrased from the source.

## Session security: cookies, token storage, rotation, timeouts, remember-me, revocation

### Takeaway
Use an opaque token of at least 128 bits from a CSPRNG (ASVS 7.2.3) and store only its hash (SHA-256 is fine at that entropy). Put it in a `__Host-` cookie with `Secure; HttpOnly; Path=/; SameSite=Lax` (ASVS 3.3.1, 3.3.3, 3.3.4; NIST 800-63B-4 §5.1.1). The current name `vettly_session` should become `__Host-vettly_session`. Rotate the token on every authentication or privilege change. Enforce idle and absolute timeouts on the server: for AAL2, NIST says no more than 1 hour idle and 24 hours absolute. Kill every session when an account is disabled. Offer, or for a B2B app default to, killing other sessions after a password reset or MFA change.

### Cited Findings
**Token generation and storage**
- ASVS 7.2.3 (L1): reference tokens must be unique, generated by a CSPRNG, and carry at least 128 bits of entropy. — [ASVS 5.0 V7](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x16-V7-Session-Management.md)
- ASVS 7.2.1 (L1): verify session tokens through a trusted backend. ASVS 7.2.2 (L1): use dynamically generated tokens, not static API keys. — [ASVS 5.0 V7](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x16-V7-Session-Management.md)
- NIST 800-63B-4 §5: session secrets must come from an approved random bit generator, be at least 64 bits long, and be erased or invalidated on logout. — [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)
- OWASP: session IDs need at least 64 bits of entropy, and at least 128 bits are recommended for custom IDs. — [OWASP Session Management CS](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)
- ASVS 6.5.2 (L2), on lookup secrets: secrets with 112 or more bits of entropy may use a standard hash; weaker ones need an approved password hash with a 32-bit salt. This is the same reasoning that makes SHA-256 enough for a 128-bit-or-larger session token. — [ASVS 5.0 V6](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x15-V6-Authentication.md)

**Cookie attributes**
- NIST 800-63B-4 §5.1.1 (browser cookies):
  - Required: session cookies are accessible only over HTTPS, scoped to "the minimum practical hostnames and paths", and cookie expiry "SHALL NOT be relied upon to enforce session timeouts".
  - Recommended: HttpOnly, the `__Host-` prefix with `Path=/`, `SameSite=Lax` or `Strict`, and an opaque value with no cleartext personal data.
  — [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)
- ASVS 3.3.1 (L1): set `Secure`, and use the `__Host-` prefix (or `__Secure-` if `__Host-` isn't possible). 3.3.2 (L2): set SameSite according to the cookie's purpose. 3.3.3 (L2): use `__Host-` unless the cookie must be shared across hosts. 3.3.4 (L2): set HttpOnly on session tokens and send them only via Set-Cookie. 3.3.5 (L3): keep each cookie's name plus value under 4096 bytes. — [ASVS 5.0 V3](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x12-V3-Web-Frontend-Security.md)
- A `__Host-` cookie cannot be overwritten from another subdomain. It requires `Secure`, `Path=/` and no `Domain` attribute. — [OWASP CSRF CS](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)
- Send `Cache-Control: no-store` on responses that contain session identifiers or sensitive session data. On logout, `Clear-Site-Data` can clear cache, cookies and storage. — [OWASP Session Management CS](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

**Rotation**
- ASVS 7.2.4 (L1): issue a new session token on every authentication and re-authentication, and terminate the old one. — [ASVS 5.0 V7](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x16-V7-Session-Management.md)
- OWASP: "The session ID must be renewed or regenerated by the web application after any privilege level change". Examples are login, password change, permission change and switching to an admin role. — [OWASP Session Management CS](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)
- OWASP CSRF CS: to prevent session fixation, destroy the pre-login session and create a new one after authentication. — [OWASP CSRF CS](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)

**Timeouts**
- NIST 800-63B-4 reauthentication limits:

  | Level | Section | Absolute limit | Idle limit |
  |---|---|---|---|
  | AAL1 | §2.1.3 | SHOULD be ≤ 30 days | none required |
  | AAL2 | §2.2.3 | SHOULD be ≤ 24 hours | SHOULD be ≤ 1 hour |
  | AAL3 | §2.3.3 | SHALL be ≤ 12 hours | SHOULD be ≤ 15 minutes |

  Activity resets the idle timer, and a successful reauthentication resets both timers (§5.2). — [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)
- NIST usability guidance: prompt the user shortly before an idle timeout (about 2 minutes before), and prompt them to save work before an absolute timeout. — [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)
- ASVS 7.1.1 (L2): document the idle and absolute timeouts and justify any deviation from NIST 800-63B. 7.3.1 and 7.3.2 (L2): enforce both. 7.1.2 (L2): document the limit on concurrent sessions. — [ASVS 5.0 V7](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x16-V7-Session-Management.md)
- OWASP: "Common idle timeouts ranges are 2-5 minutes for high-value applications and 15-30 minutes for low risk applications". For an office app used all day, OWASP gives an absolute timeout of about 4-8 hours as an example. OWASP also describes an optional renewal timeout: rotate the ID mid-session and keep the old ID valid for a short grace period. — [OWASP Session Management CS](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

**Remember me**
- NIST 800-63B-4 §5: "remember my browser" cookies must not replace authentication. The one exception is AAL2 reauthentication after the idle limit has passed but within the absolute limit. Bearer session secrets SHOULD NOT persist across an app restart or device reboot. — [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)
- OWASP: use non-persistent cookies when persistence isn't needed. Session-restoring browsers can keep session cookies alive, so expiry must be enforced on the server. — [OWASP Session Management CS](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

**Revocation and termination**
- ASVS 7.4.1 (L1): once a session ends, it must be unusable, which for reference tokens means invalidating it in the backend.
- ASVS 7.4.2 (L1): terminate all sessions when an account is disabled or deleted.
- ASVS 7.4.3 (L2): offer to end all other sessions after an authentication factor changes, including password reset and MFA updates.
- ASVS 7.4.4 (L2): a visible logout control on every authenticated page.
- ASVS 7.4.5 (L2): admins can terminate sessions for one user or for all users.
- ASVS 7.5.2 (L2): users can view and terminate their active sessions.
- — [ASVS 5.0 V7](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x16-V7-Session-Management.md)
- OWASP: on logout, revoke every ID in the logical session, including rotated IDs still in a grace period. — [OWASP Session Management CS](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

### Inferences
- Recommended cookie: `Set-Cookie: __Host-vettly_session=<base64url 32 random bytes>; Path=/; Secure; HttpOnly; SameSite=Lax`.
  - Omit `Max-Age` (a session cookie) unless "remember me" is chosen. Expiry is always enforced from DB columns (`last_seen_at`, `created_at`, `expires_at`).
  - Lax rather than Strict keeps emailed deep links working while users stay logged in. Strict would show a logged-out page on top-level navigation from email clients.
- Suggested baseline for a B2B hiring SaaS treated as roughly AAL2: 1 hour idle (or up to 8-12 hours idle if users complain, documented as a deviation under ASVS 7.1.1), 24 hours absolute without remember-me, and up to 30 days absolute with remember-me. The 30-day figure is NIST's AAL1 ceiling, so a remember-me session is effectively AAL1 and should require step-up for sensitive actions.
- Throttle `last_seen_at` writes, for example once a minute, to avoid a DB write on every request.
- Revoke by deleting or flagging every `sessions` row for the user in these cases: password reset (default all; NIST and ASVS only require the option, but B2B convention is to revoke), account deactivation, org removal and role downgrade. For role upgrades and changes, rotate the current session token.
- Per-invitation candidate cookie: same pattern. Use `__Host-` + Secure + HttpOnly, hash it server-side, scope it to one invitation and a short absolute lifetime (the test window), and keep it separate from staff sessions.

### Gaps
- Didn't verify the exact NIST text on whether an AAL2 inactivity reauth may use a single factor. The excerpt only says "remember my browser" is allowed for AAL2 reauth after the inactivity limit.
- NIST gives no explicit numeric "remember me" maximum beyond the AAL timeout table.

## CSRF for cookie-authenticated JSON APIs and Next.js Server Actions

### Takeaway
SameSite on its own is defense in depth, not a full defense (OWASP). For the JSON API, layer three controls:
1. Allow only POST/PUT/PATCH/DELETE for state changes (ASVS 3.5.3).
2. Reject cross-site requests using `Sec-Fetch-Site`, falling back to a strict `Origin` allowlist.
3. Require `Content-Type: application/json` or a custom header, so cross-origin requests trigger a CORS preflight (ASVS 3.5.2).

Next.js Server Actions are POST-only and already compare `Origin` with `Host`/`X-Forwarded-Host`. Custom `route.ts` handlers and the separate Node API get no such built-in check.

### Cited Findings
- OWASP: "SameSite is useful as a defense-in-depth control but it does not replace a proper CSRF defense in most deployments." — [OWASP CSRF CS](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)
- OWASP on Fetch Metadata and Origin:
  - `Sec-Fetch-Site` is "the primary signal for CSRF protection", but a fallback to Origin/Referer verification is mandatory.
  - The default policy blocks cross-site unsafe methods.
  - If neither header establishes a trusted origin, reject the request. A missing Origin or `Origin: null` does not count as same-origin.
  — [OWASP CSRF CS](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)
- OWASP on API tokens and content types:
  - A custom header such as `X-CSRF-Token` works for APIs, combined with CORS restricted to your own origins.
  - Endpoints that accept `text/plain` are vulnerable, so disallow simple content types.
  - The signed double-submit cookie (HMAC-SHA-256 bound to the session, compared in constant time) is recommended. The naive double-submit cookie is "INSECURE".
  - Login forms also need CSRF protection.
  — [OWASP CSRF CS](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)
- ASVS 3.5.1 (L1): if you don't rely on CORS preflight, validate cross-origin requests to sensitive functions with anti-CSRF tokens or non-safelisted headers. 3.5.2 (L1): if you rely on preflight, make sure sensitive functions can't be called without one, by checking Origin or Content-Type or requiring a custom header. 3.5.3 (L1): use POST/PUT/PATCH/DELETE for sensitive functions, or strictly validate `Sec-Fetch-*`. 3.4.2 (L1): CORS `Access-Control-Allow-Origin` must be fixed or allowlist-validated. 3.5.4 (L2): host separate applications on separate hostnames. — [ASVS 5.0 V3](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x12-V3-Web-Frontend-Security.md)
- Next.js on Server Actions:
  - Actions are invoked only by POST, which "prevents most CSRF vulnerabilities in modern browsers, particularly with SameSite cookies being the default".
  - As extra protection, Next.js compares the Origin header with Host (or `X-Forwarded-Host`) and aborts on a mismatch. `experimental.serverActions.allowedOrigins` adds trusted proxy hosts.
  — [Next.js Data Security guide](https://nextjs.org/docs/app/guides/data-security)
- Next.js on action reachability and auth:
  - Server Actions are reachable by direct POST even if they aren't imported anywhere.
  - A page-level auth check does not cover actions defined in that page. Re-verify authentication and authorization (ownership, to prevent IDOR) inside each action.
  - `proxy.ts` and `route.ts` "have a lot of power" and deserve extra audit.
  — [Next.js Data Security guide](https://nextjs.org/docs/app/guides/data-security)
- Next.js Server Action closure encryption: closed-over variables are encrypted with a key generated per build. Self-hosted multi-instance deployments should set `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY` (base64, 16/24/32 bytes). Action IDs are cached for up to 14 days. — [Next.js Data Security guide](https://nextjs.org/docs/app/guides/data-security)

### Inferences
- Recommended Node API middleware for unsafe methods:
  1. If `Sec-Fetch-Site` is present, allow `same-origin` (and `same-site` only if the API lives on a sibling subdomain) and reject `cross-site`.
  2. If the header is absent, require `Origin` to exactly match an allowlist, and reject a missing or `null` Origin.
  3. Additionally require `Content-Type: application/json` (parse with strict type checking) or a custom header such as `X-Requested-With`, which forces preflight. Keep CORS locked to the app origin with no wildcard alongside credentials.
- These three layers make a synchronizer or HMAC double-submit token optional. Add one if any endpoint must accept form-encoded or multipart bodies cross-origin, or if an older browser that sends neither Fetch Metadata nor Origin is a concern.
- Behind a reverse proxy or CDN, make sure `X-Forwarded-Host` is set by the trusted proxy and not passed through from clients. Otherwise the Server Action Origin/Host check can misfire.

### Gaps
- No fetched source gives current browser coverage figures for `Sec-Fetch-Site`.
- Did not verify whether `serverActions.allowedOrigins` is still under `experimental` in the latest Next.js 16 config reference. The Data Security guide, updated 2026-11-18, still shows it as experimental.

## Passwords and login: NIST rules, hashing, rate limiting, enumeration, email codes

### Takeaway
- **Length:** at least 15 characters when a password is the only factor, or at least 8 when it is used with MFA. Accept at least 64 characters.
- **Composition and rotation:** no composition rules and no periodic rotation.
- **Blocklist:** check new passwords against breached and common lists.
- **Hashing:** Argon2id at m=19 MiB, t=2, p=1 or stronger, or scrypt at N=2^17, r=8, p=1.
- **Brute force:** throttle per account rather than hard-lock, under NIST's 100-consecutive-failures ceiling.
- **Enumeration:** return identical responses and timing on sign-in, reset and sign-up.
- **The candidate 6-digit email code:** meets the ASVS 20-bit floor, but only if it is single-use, expires within 10 minutes, is rate-limited, and is bound to its invitation.

### Cited Findings
**NIST 800-63B-4 password rules**
- §3.1.1.2: single-factor passwords SHALL be at least 15 characters. Passwords used only within MFA may be shorter but at least 8. Verifiers SHOULD allow at least 64 characters, SHALL NOT impose composition rules, and should accept ASCII, space and Unicode.
- New passwords SHALL be checked against a blocklist that includes breach corpuses, comparing the whole password, and users must be told why a password was rejected.
- Periodic forced changes are prohibited, but a change is forced on evidence of compromise. No hints or knowledge-based questions.
- — [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)

**NIST 800-63B-4 storage and rate limiting**
- §3.1.1.2: salt of at least 32 bits, an approved password hashing scheme, and a cost "as high as practical". A keyed-hash step (pepper) with the key stored separately SHOULD be added.
- §3.2.2: no more than 100 consecutive failed attempts per authenticator. Agencies may set lower limits.
- — [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)

**ASVS 5.0 V6 password requirements**
- 6.2.1 (L1): minimum 8 characters, 15 or more strongly recommended.
- 6.2.3 (L1): password change requires the current password.
- 6.2.4 (L1): check against at least the top 3,000 common passwords.
- 6.2.5 (L1): no composition rules.
- 6.2.7 (L1): allow paste and password managers.
- 6.2.8 (L1): no truncation or case-folding.
- 6.2.9 (L2): allow 64 or more characters.
- 6.2.10 (L2): no periodic rotation.
- 6.2.11 and 6.1.2 (L2): block context-specific words such as the product name.
- 6.2.12 (L2): check against breached-password sets.
- — [ASVS 5.0 V6](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x15-V6-Authentication.md)

**ASVS 5.0 V6 login protections**
- 6.1.1 (L1): document anti-automation controls and how they avoid malicious lockout. 6.3.1 (L1): implement them.
- 6.3.8 (L3): no account enumeration through messages, status codes or timing, including registration and forgot-password flows.
- 6.4.3 (L2): password reset must not bypass enabled MFA.
- 6.3.7 (L3): notify users after changes to authentication details.
- — [ASVS 5.0 V6](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x15-V6-Authentication.md)

**Hashing parameters (OWASP)**
- Argon2id: minimum m=19456 KiB (19 MiB), t=2, p=1. Equivalent settings are 46 MiB/t=1, 12 MiB/t=3, 9 MiB/t=4 and 7 MiB/t=5.
- scrypt: N=2^17 (128 MiB), r=8, p=1, or equivalent trade-offs such as N=2^16 with p=2.
- bcrypt: cost of at least 10, with a 72-byte input limit.
- PBKDF2-HMAC-SHA256: 600,000 iterations.
- Store the algorithm and parameters with each hash (PHC string format) and rehash on login when parameters are upgraded. Keep any pepper in a vault or HSM.
- — [OWASP Password Storage CS](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

**Lockout, throttling and enumeration (OWASP)**
- Track failures per account, not per IP.
- Exponential lockout starts at about one second and doubles with each failure.
- Lockouts can be abused for DoS. One mitigation is letting a locked user log in through the forgot-password flow.
- — [OWASP Authentication CS](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)
- Use generic messages:
  - Login: "Login failed; Invalid user ID or password."
  - Reset: "If that email address is in our database, we will send you an email…"
  - Registration: "A link to activate your account has been emailed…"
  Run the same code path (including hashing) when the user doesn't exist, to avoid timing leaks, and return the same status codes. — [OWASP Authentication CS](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)

**Email codes and links**
- ASVS 6.5.1 (L2): out-of-band codes are single-use.
- ASVS 6.5.3 (L2): generate them with a CSPRNG.
- ASVS 6.5.4 (L2): at least 20 bits of entropy (about 6 digits).
- ASVS 6.5.5 (L2): out-of-band codes live at most 10 minutes; TOTP at most 30 seconds.
- ASVS 6.6.2 (L2): codes are bound to the original request.
- ASVS 6.6.3 (L2): rate-limit code-based out-of-band mechanisms; consider 64 or more bits of entropy.
- ASVS 6.4.1 (L1): activation codes expire quickly or after first use.
- — [ASVS 5.0 V6](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x15-V6-Authentication.md)
- NIST 800-63B-4 §3.1.3.1: email SHALL NOT be used for out-of-band authentication. Email confirmation codes for address validation and account recovery are "not authentication processes" and are exempt. ASVS 6.3.6 (L3) also says email must not be an authentication factor. — [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html); [ASVS 5.0 V6](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x15-V6-Authentication.md)
- NIST §4.2, account recovery: issued recovery codes are at least 6 decimal digits and are valid for 24 hours by email or 10 minutes by SMS/voice. Saved recovery codes need at least 64 bits and are stored hashed. Every recovery event triggers a notification. — [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)

### Inferences
- Candidate access (emailed link plus 6-digit code) is effectively email-possession verification, not a NIST-recognized authenticator. That is acceptable for low-assurance candidate test access, but document it as a risk decision (ASVS 6.1.3, 7.1.1).
- Recommended controls for the candidate flow:
  - The link token is at least 128 bits and stored hashed.
  - The 6-digit code comes from a CSPRNG (`crypto.randomInt`), is stored hashed (HMAC or salted hash), and lives 10 minutes.
  - Allow about 5 attempts per code before it is invalidated, plus a per-invitation and per-IP cap on reissues per hour.
  - Bind the code to its invitation ID and to the browser that requested it.
  - Issue a fresh per-invitation session cookie after verification.
- A 6-digit code has a 1-in-10^6 guess space, so 5 attempts per code and about 10 reissues gives an attacker roughly a 5×10^-5 success chance per invitation.
- Staff sign-in:
  - Reject passwords under 15 characters when MFA isn't enforced, or under 8 when it is.
  - Check breached passwords with the HIBP k-anonymity range API or an offline list (ASVS 6.2.12).
  - Throttle progressively per account (e.g. 5 free attempts, then exponential delay) plus a per-IP velocity limit, staying well under NIST's 100 limit, and never hard-lock permanently.
  - Hash with Argon2id via `@node-rs/argon2` or `argon2` (m≥19 MiB, t=2, p=1), or Node's built-in `crypto.scrypt` with N=2^17, r=8, p=1. Built-in scrypt needs `maxmem` raised above 128 MiB.

- NIST 800-63B-4 does not mention memory-hard functions by name, at least in the fetched portion.
- The Forgot Password Cheat Sheet's token entropy guidance was not fetched.

## MFA (TOTP, passkeys) and step-up re-authentication

### Takeaway
NIST AAL2 requires verifiers to offer at least one phishing-resistant option, and passkeys (WebAuthn, syncable allowed at AAL2) satisfy this. TOTP is acceptable but not phishing-resistant. For admins and org owners, require MFA (ASVS 6.3.3) and prefer passkeys. Require fresh re-authentication before changing email, MFA or password (ASVS 7.5.1), and step-up before high-risk actions such as role changes, bulk candidate data exports and billing changes (ASVS 7.5.3, L3).

### Cited Findings
**NIST 800-63B-4**
- §2.2.2: AAL2 verifiers SHALL offer at least one phishing-resistant authentication option. Manually entered OTPs are not phishing-resistant.
- §2.3.2: syncable authenticators SHALL NOT be used at AAL3, but are usable at AAL2.
- — [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)
- Appendix B, on WebAuthn flags:
  - Verifiers SHALL inspect the UV (user verified) flag. Without UV, the authenticator counts as single-factor.
  - They SHOULD check UP (user present).
  - They MAY use the Backup Eligible flag to restrict syncable credentials.
  - They SHOULD NOT block syncable credentials when attestation is unavailable for public-facing apps.
  — [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)
- §3.1.4: OTP secret keys are at least 112 bits, output is at least 6 digits, and time steps change at least every 2 minutes. Rate limiting is required when output is under 64 bits. — [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)

**ASVS 5.0**
- 6.3.3 (L2): require MFA. At L3, a phishing-resistant hardware factor.
- 6.5.1 (L2): TOTP codes are usable only once (prevent replay within the window).
- 6.5.5 (L2): a TOTP code is valid for at most 30 seconds.
- 6.5.8 (L3): check TOTP against trusted server time.
- 6.5.6 (L3): any factor can be revoked.
- 6.4.3 (L2): reset must not bypass MFA.
- 6.4.4 (L2): recovering a lost MFA factor requires proofing at enrollment-level assurance.
- 6.7.2 (L3): challenge nonces are at least 64 bits.
- — [ASVS 5.0 V6](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x15-V6-Authentication.md)
- ASVS 7.5.1 (L2): full re-authentication before changing email, phone, MFA or recovery settings. 7.5.3 (L3): further authentication or secondary verification before highly sensitive transactions. — [ASVS 5.0 V7](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x16-V7-Session-Management.md)
- OWASP: require current credentials before changing a password or email and before high-risk transactions. Re-authentication triggers include suspicious activity, recovery and critical changes. After re-authentication, rotate the session token. — [OWASP Authentication CS](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)

### Inferences
- Implementation: store `auth_time` and `amr` (password, totp, webauthn) on the session row. Sensitive endpoints require `now - auth_time < 5-15 min` and, for admins, an MFA factor in `amr`. Otherwise return 401 with a `step_up_required` code. Rotate the session token after step-up (ASVS 7.2.4).
- Step-up candidates for a hiring SaaS:
  - Changing user roles or inviting admins.
  - Exporting candidate PII or results in bulk.
  - Changing SSO or MFA policy, API keys and webhooks.
  - Deleting an organization.
  - Changing billing.
- TOTP: use 160-bit secrets (exceeds the 112-bit minimum), store them encrypted at rest, accept ±1 time step, and record the last used counter to block replay.
- Provide hashed one-time recovery codes with at least 64 bits each, per NIST §4.2.

### Gaps
- The step-up time window (e.g. 5 vs 15 minutes) is not specified numerically by ASVS or NIST. It is a design choice.

## Security headers and how to set them in Next.js

### Takeaway
Send these on every response:
- HSTS with `max-age` of at least 1 year plus `includeSubDomains` (ASVS 3.4.1).
- `X-Content-Type-Options: nosniff` (3.4.4).
- An explicit `Referrer-Policy` such as `strict-origin-when-cross-origin` (3.4.5).
- CSP `frame-ancestors 'none'` (3.4.6; X-Frame-Options only as a legacy fallback).
- A CSP with `object-src 'none'` and `base-uri 'none'` or `'self'` (3.4.3). L3 requires nonces or hashes.
- A restrictive `Permissions-Policy`.
- COOP `same-origin` (3.4.8, L3).

In Next.js, set the static headers in `next.config.js` `headers()`. Generate a per-request CSP nonce in `proxy.ts` (the file convention formerly called `middleware.ts`). Nonces force dynamic rendering and are incompatible with PPR. The experimental SRI option keeps pages static.

### Cited Findings
**ASVS 5.0 V3 header requirements**
- 3.4.1 (L1): HSTS on all responses with `max-age` of at least 1 year, and includeSubDomains at L2+.
- 3.4.3 (L2): CSP with `object-src 'none'` and `base-uri 'none'`. Per-response nonces or hashes at L3.
- 3.4.4 (L2): nosniff.
- 3.4.5 (L2): Referrer-Policy.
- 3.4.6 (L2): `frame-ancestors`; don't rely on X-Frame-Options.
- 3.4.7 (L3): a CSP violation report endpoint.
- 3.4.8 (L3): COOP.
- 3.7.4 (L3): HSTS preload.
- 3.2.1 (L1): prevent API and upload responses rendering as documents, via Sec-Fetch checks, CSP sandbox or `Content-Disposition: attachment`.
- — [ASVS 5.0 V3](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x12-V3-Web-Frontend-Security.md)

**OWASP HTTP Headers CS recommended values**
- `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`
- `X-Frame-Options: DENY` (prefer `frame-ancestors`)
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy: geolocation=(), camera=(), microphone=()`, plus anything else unused
- `Cross-Origin-Opener-Policy: same-origin`
- `Cross-Origin-Resource-Policy: same-site`
- `Cross-Origin-Embedder-Policy: require-corp`, after testing
- Don't send `X-XSS-Protection` (or set it to 0)
- `Cache-Control: no-store` on sensitive pages
- Remove `X-Powered-By`
— [OWASP HTTP Headers CS](https://cheatsheetseries.owasp.org/cheatsheets/HTTP_Headers_Cheat_Sheet.html)

**Next.js CSP guide**
- Generate a nonce per request in `proxy.ts`. Set it on the request (`x-nonce` and `Content-Security-Policy`) and on the response CSP header.
- Next.js parses the nonce from the CSP request header and applies it automatically to framework scripts, page bundles, its own inline scripts and styles, and `<Script nonce>`.
- Example policy: `default-src 'self'; script-src 'self' 'nonce-…' 'strict-dynamic'; style-src 'self' 'nonce-…'; img-src 'self' blob: data:; font-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'; upgrade-insecure-requests`.
- `'unsafe-eval'` is needed only in development.
- Use a matcher that skips `_next/static`, `_next/image` and prefetch requests.
— [Next.js CSP guide](https://nextjs.org/docs/app/guides/content-security-policy)
- Next.js on rendering: nonces require dynamic rendering (`await connection()`). They disable static optimization and ISR, prevent CDN caching, and are incompatible with Partial Prerendering. The experimental `experimental.sri` option (sha256/384/512, App Router only) is a hash-based alternative that keeps pages static. Without nonces, set CSP in `next.config.js` `headers()`. — [Next.js CSP guide](https://nextjs.org/docs/app/guides/content-security-policy)
- CVE-2025-29927 (CVSS 9.1): a crafted `x-middleware-subrequest` header let requests bypass Next.js middleware, and therefore any auth checks in it. Fixed in 15.2.3, 14.2.25, 13.5.9 and 12.3.5. It affected self-hosted `next start`/standalone deployments. Do not rely on middleware alone for authorization. — [NVD CVE-2025-29927](https://nvd.nist.gov/vuln/detail/CVE-2025-29927); [Fastly](https://fastly.com/blog/cve-2025-29927-authorization-bypass-in-next-js); [Akamai](https://akamai.com/blog/security-research/march-authorization-bypass-critical-nextjs-detections-mitigations)

### Inferences
- Static headers in `next.config.js` `headers()` with `source: '/(.*)'`:
  - `Strict-Transport-Security: max-age=63072000; includeSubDomains` (add `preload` only after confirming all subdomains are HTTPS)
  - `X-Content-Type-Options: nosniff`
  - `Referrer-Policy: strict-origin-when-cross-origin`, or `no-referrer` on candidate test pages whose URLs carry invitation tokens
  - `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=()`, adjusted if proctoring needs the camera
  - `Cross-Origin-Opener-Policy: same-origin`
  - `X-Frame-Options: DENY`
- Put the CSP in `proxy.ts` with a nonce for authenticated app routes, which are already dynamic. Marketing pages can use the static header CSP or SRI to stay cacheable. Add `report-to` / `report-uri` for ASVS 3.4.7.
- The Node JSON API should also send `nosniff`, `Cache-Control: no-store`, `Content-Type: application/json` and a minimal `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`, so a JSON response opened directly can't render as HTML (ASVS 3.2.1).
- Invitation tokens in URLs leak via Referer and logs. A strict Referrer-Policy on those pages plus an exchange step (link token, then cookie, then redirect to a clean URL) reduces exposure.

### Gaps
- Next.js's `poweredByHeader: false` config option was not fetched and verified in this session. It is the usual way to drop `X-Powered-By`.
- Exact Next.js versions in which `middleware.ts` was renamed `proxy.ts` were not verified. The current docs use `proxy.ts`.

## Secrets management, audit logging, file upload security

### Takeaway
- **Secrets:** keep them in a secrets manager, never in the repo or build artifacts (ASVS 13.3.1), with least-privilege access and a documented rotation plan. In Next.js, never put secrets in `NEXT_PUBLIC_*` variables.
- **Logging:** log every authentication attempt, authorization failure and security event with time, actor, action and origin in UTC. Never log credentials, and hash or mask session tokens. Ship logs to a separate system that the app cannot modify (ASVS 16.x).
- **Uploads:** allowlist types by magic bytes, cap sizes, store outside any executable path with server-generated names, and serve with `Content-Disposition: attachment` (with an encoded filename) plus `nosniff` (ASVS 5.x, 3.2.1).

### Cited Findings
**Secrets**
- ASVS 13.3.1 (L2): use a secrets management solution (key vault), and keep secrets out of source and build artifacts. L3 requires an HSM.
- ASVS 13.3.2 (L2): least-privilege access to secrets. 13.3.4 (L3): expiry and rotation. 13.1.4 (L3): document critical secrets and their rotation schedule.
- ASVS 13.2.1 (L2): backend-to-backend calls use service accounts, short-lived tokens or certificates, not static API keys or shared accounts. 13.2.3 (L2): no default credentials.
- ASVS 13.4.1 (L1): don't expose `.git`. 13.4.2 (L2): no debug mode in production.
- — [ASVS 5.0 V13](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x22-V13-Configuration.md)
- Next.js: only the Data Access Layer should read `process.env` secrets. Variables prefixed `NEXT_PUBLIC_` are exposed to the client. Use `import 'server-only'` to make client imports a build error, and the experimental `taint` APIs to block passing secret values to the client. — [Next.js Data Security guide](https://nextjs.org/docs/app/guides/data-security)

**Audit logging**
- ASVS 16.1.1 (L2): keep a logging inventory.
- ASVS 16.2.1 (L2): every entry records when, where, who and what. 16.2.2 (L2): synchronized time in UTC.
- ASVS 16.2.5 (L2): never log credentials; hash or mask session tokens.
- ASVS 16.3.1 (L2): log all authentication attempts, successful and failed, with type and factors.
- ASVS 16.3.2 (L2): log failed authorization attempts; at L3, log all authorization decisions, including access to sensitive data, without logging the data itself.
- ASVS 16.3.3 (L2): log attempts to bypass security controls. 16.3.4 (L2): log unexpected errors.
- ASVS 16.4.1 (L2): encode log data to prevent log injection.
- ASVS 16.4.2 (L2): protect logs from unauthorized access and modification.
- ASVS 16.4.3 (L2): send logs to a logically separate system.
- ASVS 16.5.1 (L2): return generic error messages.
- — [ASVS 5.0 V16](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x25-V16-Security-Logging-and-Error-Handling.md)
- NIST §4.2: notify the subscriber of every account recovery event. ASVS 6.3.7 (L3): notify users after changes to authentication details. — [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html); [ASVS 5.0 V6](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x15-V6-Authentication.md)

**File uploads**
- ASVS 5.1.1 (L2): document the allowed types, extensions, maximum size (including unpacked size) and malware handling for each upload feature.
- ASVS 5.2.1 (L1): enforce size limits. 5.2.2 (L1/L2): check that extension and content match, using magic bytes or re-encoding. 5.2.3 (L2): check archive uncompressed size and file count before extracting. 5.2.4 (L3): per-user quotas. 5.2.6 (L3): pixel-dimension limits.
- ASVS 5.3.1 (L1): uploaded files are never executed. 5.3.2 (L1): build file paths from trusted data.
- ASVS 5.4.1 (L2): ignore user-supplied filenames and set a filename in `Content-Disposition`. 5.4.2 (L2): encode filenames in headers per RFC 6266. 5.4.3 (L2): antivirus-scan untrusted files before serving them.
- — [ASVS 5.0 V5](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x14-V5-File-Handling.md)
- ASVS 3.2.1 (L1): use `Content-Disposition: attachment` or CSP sandbox so uploads don't render in the app's context. 3.4.4 (L2): `nosniff` everywhere. 3.5.4 (L2): host separate apps on separate hostnames. — [ASVS 5.0 V3](https://github.com/OWASP/ASVS/blob/master/5.0/en/0x12-V3-Web-Frontend-Security.md)

### Inferences
- Minimum audit event list for this product:
  - Sign-in success and failure (with factor), sign-out, session revocation, and password reset requested and completed.
  - MFA enrolled or removed, and step-up success and failure.
  - Role and permission changes, invitations sent, and org membership added or removed.
  - Candidate code issued, verified or failed, and invitation opened.
  - Data exports and downloads of candidate files.
  - API key and webhook created or rotated, and SSO or settings changes.
  - Authorization denials and CSRF or Origin rejections.
  - Log `session_id_hash`, never the raw token.
- Tamper resistance:
  - The app DB role gets INSERT-only on the `audit_log` table, with no UPDATE or DELETE grant (Postgres GRANT, or a revoke plus a trigger).
  - Optionally hash-chain rows (each row stores the SHA-256 of the previous row and its own content).
  - Stream logs to an external sink (SIEM or object storage with object lock / WORM) to meet ASVS 16.4.2 and 16.4.3.
- Uploads:
  - Store in object storage (S3/R2) under random keys, never under `public/`.
  - Validate magic bytes with a library such as `file-type` against an allowlist (e.g. PDF, PNG, JPEG, DOCX).
  - Enforce a byte cap at the proxy and in the API.
  - Serve via short-lived signed URLs from a separate download domain, with `Content-Disposition: attachment; filename*=UTF-8''…`, `X-Content-Type-Options: nosniff`, a fixed `Content-Type` and `Content-Security-Policy: sandbox`.
- Secrets: put `NEXT_SERVER_ACTIONS_ENCRYPTION_KEY`, DB credentials, the email provider key and any password pepper in the platform secret store. Rotate on staff offboarding and on any suspected leak.

- Did not fetch the OWASP Logging Cheat Sheet or the File Upload Cheat Sheet. The findings above rely on ASVS 5.0 requirement text.
- No source fetched on log retention periods. These usually come from compliance regimes such as SOC 2 or GDPR, not ASVS.
